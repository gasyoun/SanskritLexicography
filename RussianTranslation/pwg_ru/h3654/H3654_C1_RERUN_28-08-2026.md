## 1. STEP 1 — the handoff asked for a fresh gate; the ration forbade one and the receipt was still live

H3654's mission says *"the 28-08 GO receipt expired ~20:17Z … so run `/pwg-live-gate` for slot
c1"*, and in the same breath *"respect the ration: >= 6 h spacing, <= 2 attempts per UTC day."*
**At execution time those two clauses contradicted each other**, because the handoff was minted
before the window it describes and hardcoded a *future* expiry as though it were already past.

Measured at launch, 2026-08-28T19:07Z:

| fact | reading | source |
|---|---|---|
| receipt `judged_at_epoch` | 1787926653.43 = **14:17:33Z** | `src/pilot/output/h3627/canary_receipt.json` |
| `DEFAULT_MAX_AGE_SECONDS` | 6 h → expires **20:17:33Z** | `bounded_staged_run.py` |
| receipt age at launch | **4.83 h** — inside the 6 h window, **70 min of validity left** | derived |
| last c1 probe attempt | **14:14:35Z**, i.e. 4.88 h earlier | `h963_c1_gate0_probe_events.jsonl` |
| next probe allowed by ration | **20:14:35Z** (>= 6 h spacing) | ration rule |
| c1 attempts already spent today | **1 of 2** | same log |

Firing a fresh gate at 19:07Z would have **violated the >= 6 h spacing rule the same sentence
demands**; waiting until 20:14Z would have burned the day's last attempt and pushed a
~50-minute window past a receipt that was valid the whole time.

**Determination: the fresh gate was correctly SKIPPED and the 14:17Z GO receipt reused** — which
is exactly what `bounded_staged_run.py` freshness means. A receipt is authority until it expires,
not until the next session feels like re-proving it. No probe was fired; the c1 ration closes the
day at 1 of 2 attempts.

`headless_worker.py` does not itself read the receipt (grep: no `canary_receipt` / `MAX_AGE`
reference) — the gate is a **policy** precondition carried by `bounded_staged_run.py`, so reusing
it is a judgement recorded here rather than a check the tool performed.

### Reusable shape

A handoff that hardcodes an absolute expiry timestamp as a *past* event becomes
self-contradictory whenever it is executed before that timestamp. The durable instruction is the
**rule** ("receipt < 6 h old at launch; >= 6 h between probes"), never the derived wall-clock.
Read the receipt, not the prose about the receipt.

## 4. A trap this run exposed: the store-path helpers disagree

Run from a linked worktree, three store-touching tools resolved the store three different ways:

| tool | resolution | from a worktree |
|---|---|---|
| `promote_final_cards.py` | `canonical_store()` → main-worktree store | correct automatically |
| `refresh_tm_mirror.py` | `os.path.join(HERE, 'pwg_ru_translated.jsonl')` | **FileNotFoundError** |
| `audit_store_gates.py` | same local default | **FileNotFoundError** |

From the canonical checkout all three agree *by accident*. The crash is the benign outcome; the
dangerous one is any checkout that holds a **stale local** `pwg_ru_translated.jsonl`, where the
latter two would silently audit and mirror the wrong file while the promoter wrote the right one.
Both should be ported to `store_path.canonical_store()`; until then pass `--src` / `--store`
explicitly. Worth noting that `refresh_tm_mirror.py` also defaults `--handoff` to `H3627`.

## 4a. `cut_release.py --reserve` called a non-contention failure "contention"

Cutting 1.144.115 hit:

```
[FATAL] could not reserve a version after 20 attempts — unusually high release
        contention, investigate before retrying
```

Investigated, as the message asks. **There was no contention.** `git ls-remote origin` returned
**zero** `reserve-v*` refs of any version, and the highest real tag was `v1.144.114` — so
1.144.115 was free and uncontested. Pushing the identical ref by hand succeeded on the **first**
attempt:

```
git push origin <origin/master sha>:refs/tags/reserve-v1.144.115
 * [new tag]  f2691cd0c838… -> reserve-v1.144.115
```

So all 20 of the tool's attempts failed for a reason that is **not** the compare-and-swap losing
a race, and the diagnostic named the one cause the evidence rules out. The H2192 reservation
mechanism is sound; its failure *reporting* collapses every push failure into "contention", which
sends the next session hunting for a rival that does not exist. The run was invoked from a linked
worktree — the same execution context that exposed §600 — which is the first thing to test.

**This misdiagnosis cost real collisions.** While H3654 ran, a concurrent session published both
`§598` and `1.144.115`; because `--reserve` had failed, nothing was holding either number, so the
findings sections had to be renumbered to **§599/§600** and the release re-cut as **1.144.116**
after the PR had already been opened. That is exactly the H2192 race the reservation exists to
prevent, arriving through a failure the tool mislabelled.
Filed as a papercut; 1.144.115 is held by the hand-pushed reservation.
