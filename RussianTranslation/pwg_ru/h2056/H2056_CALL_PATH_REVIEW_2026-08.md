## Q1 — Where the rate-limit signal is lost

The signal is lost at exactly two lines — [max_account_orchestrator.py:1180-1182](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/max_account_orchestrator.py#L1180) and [headless_worker.py:589-603](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/headless_worker.py#L589) — because both `except subprocess.TimeoutExpired` handlers on the paid path assign the string `'timeout'` without ever reaching a classifier, and the text that would prove a 429 is destroyed one level below them at [proc_tree.py:270/280](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/proc_tree.py#L270).

**`_probe_err_class` is pure text matching over a string the caller supplies.** [max_account_orchestrator.py:1113-1120](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/max_account_orchestrator.py#L1113) has three branches in order: an auth regex → `'auth'`; `RATE_LIMIT.search(text)` (`rate.?limit|usage limit|too many requests|429`, [mao:50](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/max_account_orchestrator.py#L50)) → `'rate_limit'`; fall-through → `None`, which every caller turns into `'process'`. It is called from exactly two sites, both requiring a live `proc` object: [mao:1197](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/max_account_orchestrator.py#L1197) after a non-zero returncode, and [mao:1212](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/max_account_orchestrator.py#L1212) after rc=0 with an error envelope. So `'rate_limit'` requires all of: the CLI terminated inside the 300 s ceiling; it exited non-zero or returned a well-formed error envelope; and the literal quota words appear in the captured text. Miss one and the label is unreachable.

**The structure, not a heuristic, is what fails.** Every function in the tree that can emit `rate_limit` takes a completed process as input — `_probe_err_class`, `classify_process` ([headless_worker.py:423](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/headless_worker.py#L423), sole caller guarded by `if proc.returncode:` at :636), and `is_rate_limited` ([mao:65](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/max_account_orchestrator.py#L65)). None is reachable from either timeout handler. On 24-07/25-07 the CLI exited non-zero quickly enough to land on mao:1197 and matched; on 31-07 it stayed alive retrying past 300 s and landed on mao:1180. **The branch is selected by the CLI's exit behaviour, never by the provider's condition.**

**The wall-vs-API comparison does not exist, and the premise that `call_reservation` already parses those fields is false.** `telemetry_from_cli_wrapper` ([call_reservation.py:52-78](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/call_reservation.py#L52)) reads exactly `usage.input_tokens`, `usage.output_tokens`, `usage.cache_read_input_tokens`, `usage.cache_creation_input_tokens` and `total_cost_usd`. A grep of the whole `src/` tree for `duration_api_ms`, `duration_ms`, `num_turns`, `session_id` returns **zero** hits against the CLI envelope (the only matches are `durationMs` in the unrelated h1210 Workflow-transcript collectors and one selftest note string).

**Output from a killed subprocess is captured, then deliberately discarded twice.** `run_tree_kill` kills the tree and re-runs `communicate()` at [proc_tree.py:270](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/proc_tree.py#L270) explicitly to drain the pipes, binding the CLI's real stdout/stderr into locals — then re-raises the original exception at :280 with only `cleanup_trouble` attached. On Windows CPython the first `communicate()` raises `TimeoutExpired` with no output attached at all, so that discarded local is the only copy that ever existed in the parent. Compounding it, `run_claimed` writes the attempt log only on the non-timeout path ([mao:507-509](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/max_account_orchestrator.py#L507)), so a worker timeout leaves an `attempt_log_path` in sqlite pointing at a file that was never written. And the operator-facing verdict actively misdirects: [h963_c4_gate0_probe.py:127](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/h963_c4_gate0_probe.py#L127) puts `'timeout'` in `CONN_ERR_CLASSES`, so a quota state is reported as `measured connection/process error (timeout)` — pointing the diagnosis at the connectivity branch of an exclusion ladder FINDINGS §266-271 had already closed.

## Q4 — Cost attribution across retries

**(a) The durable ledger SUMS every attempt; every per-window artifact keeps only the LAST attempt; no per-card cost figure exists at all.** Each `HeadlessEngine.call` — including each `.retryN` — takes its own pre-spawn `reserve()` and its own `finalize()`, accumulating at [call_reservation.py:345-347](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/call_reservation.py#L345), idempotent per `reservation_id`. **(c) `STOP_COST_UNEVALUABLE` keys off "we reserved a call we could not price", NOT off "we saw an unevaluable envelope" — correct on that axis.** `reserve()` sets `cost_evaluable = False` and increments `pending_calls` **before** the spawn, and the flag returns to True only when both counters are zero — monotonically unreachable once any call is unevaluable. The exposure is elsewhere: both stops short-circuit on `budget_cap is not None`.

## Method and limits

**Protocol.** One mapping agent partitioned the seven in-scope files across five review agents, one per question. Each reviewer produced an answer plus candidate findings. Every candidate was then re-examined independently by three verification agents under distinct adversarial lenses:

- **correctness** — does the cited code say what the finding claims, and does the claimed mechanism hold on a full read of the surrounding control flow?
- **reproduces** — trace the stated inputs through the code to the stated output; does the specific wrong output actually result?
- **already-handled** — is there a guard, mitigation, downstream correction, documented ruling, or repo record that makes this a non-issue or a known accepted trade?

All three lenses were **refute-primed**: each was instructed to try to kill the finding, and a finding surviving all three by default carries no credit for consensus it did not earn. **Default-to-refuted rule: 2 of 3 refutations kills the finding.** 1 of 3 downgrades it to PLAUSIBLE and the refuting argument is reproduced above alongside the upholding ones. 0 of 3 is CONFIRMED.

**Counts.** 22 agents (1 map · 5 review · 15 verify · 1 synthesise), Opus 5 (`claude-opus-5[1m]`) throughout. 24 findings raised, 72 lens passes, 13 survivors, 11 killed. Two refutations were unanimous (Q2-F4, Q3-F4); four findings survived all three lenses untouched (Q1-F1 through Q1-F4 plus Q1-F5, Q2-F1, Q3-F1).

**Zero paid calls were made.** No `claude` invocation, no gate run, no probe. c4 is rate-limited; the whole review is static reading. Several findings are explicitly gated on measurements that can be taken from **existing ledger files on disk** without a paid call — rank 10 above is the main one.

**What this review did NOT do.**

- **No fixes were applied.** No file was edited or created. Every "proposed fix" column is a proposal for a human to rank.
- **No ceiling was changed.** `PROBE_LATENCY_CEILING_MS`, `HARD_TIMEOUT_MS` and the 300 s probe literal are all reported as-is; P1 and Q2-F1 are surfaced as open questions, not adjustments.
- **No gate was re-run and no measurement was re-taken.** All numeric claims are either quoted from the anchored §270 record, from the repo's own committed reports, or from `git log`.
- **Nothing settled in FINDINGS §266-271 was re-litigated.** The exclusion ladder (profile, flags, Node shim, cwd/trust, process contention, connectivity, auth, startup, telemetry env, proxy, model) and the CRLF/eol phantom-dirty loop are closed and were treated as closed.

**Scope leakage worth flagging.** Four surviving findings anchor on files **outside** the declared in-scope table: [proc_tree.py](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/proc_tree.py) (Q1-F3), [audit_window.py](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/audit_window.py) (Q3-F1) and [perf_preflight.py](https://github.com/gasyoun/SanskritLexicography/blob/master/RussianTranslation/src/pilot/perf_preflight.py) (Q5-F1), with supporting evidence from `requeue_from_audit.py`, `no_pwg_residual_ledger.py`, `sense_count.py`, `no_pwg_scale_plan.py` and `gen_opt_harness2.py`. None was refuted on that ground, because in each case the harm lands on an in-scope file — but it means **the in-scope-seven boundary does not contain the defect surface.** Q1-F3 in particular is the root blocker for the two highest-ranked in-scope findings and sits entirely outside the reviewed set.

**Out of scope and untouched:** translation quality, prompt content, the store/promoter, and everything under `pwg_ru/` that is data rather than code.
