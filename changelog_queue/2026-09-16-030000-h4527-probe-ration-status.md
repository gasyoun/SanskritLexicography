- **H4527 — the readiness-probe ration can be READ without spending an attempt on it.** H4915 made the ration a code gate (at most 2 attempts per UTC day per profile, at least 6 h apart, one machine-wide ledger), but left it observable only by *attempting* a probe: `probe_fleet` and `_probe_call` raise `ProbeRationRefused`, and that was the only surface. Two consecutive H4527 passes (15-09, 16-09) therefore learned the lane was closed by hand-grepping a JSONL under `%TEMP%`, and a batch drain — which claims a handoff *before* it reads anything — cannot do even that, which is how a dispatch was handed out against a closed lane twice. New read-only subcommand `max_account_orchestrator.py probe-ration [--account NAME]`: it prints, per validated profile, the attempts recorded on the current UTC day, the last attempt, the next legal UTC time and `legal_now`, as `pwg.probe_ration_status.v1`. Exit 0 = a probe is legal now for every reported profile · 3 = at least one is rationed · 1 = the ledger is unreadable (fail closed, the same verdict the gate gives), so a dispatcher branches on an exit code instead of parsing prose. It spawns nothing, writes nothing — not even to the ration ledger — and reads the ration through `ProbeRation` itself rather than a second copy of the arithmetic, so the report cannot drift from what `probe_fleet` will actually do. Two public epoch helpers (`execution_contract.utc_day`, `utc_iso_ts`) exist for the same reason: the reporter compares UTC days the way `ProbeRation.check` does, not the way it guesses. Pin `_test_h4527_probe_ration_status_is_readable_without_probing` asserts exit 3 when rationed, exit 0 when legal, zero spawns and a byte-identical ledger either way, and that an unknown `--account` refuses rather than reporting a falsely green empty set. Eight LANG_PARITY entries re-derived across the touched files; every verdict stands (the reporter takes no `--lang` and reads no card, so RU and EN see the identical report).
